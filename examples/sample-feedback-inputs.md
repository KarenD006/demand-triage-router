# 示例输入

## 示例 1：进入需求池，状态为待执行

输入：

```text
客户说：能不能支持批量导出项目数据？他们每周都要整理项目进度给老板看，现在需要一个个复制，很费时间。
来源：销售群
客户类型：企业客户
```

处理：

- 拟写入池子：`需求池`
- 需求状态：`待执行`
- 优先级：`P2`
- 内部预处理字段：用户类型 `企业客户`，来源渠道 `销售`，影响范围 `单个用户` 或 `核心客户`（视客户重要性），业务价值 `中`。
- 模式：日常收件模式，直接写入。
- 轻反馈：`已收进需求池：待执行 / P2`，标题 `项目数据批量导出以支持周报汇报`。
- 原因：场景和痛点清楚，已经可以进入产品处理；仍需补充导出字段、格式和影响客户数。

## 示例 2：进入 Bug池

输入：

```text
用户截图反馈：保存设置时报错 500。昨天还能保存，今天三个账号都失败。
来源：客服工单
```

处理：

- 拟写入池子：`Bug池`
- Bug 状态：`待复现`
- 严重程度：`S1严重`。
- 内部预处理字段：来源渠道 `客服`，环境信息记录缺失项，影响范围可从“三个账号都失败”判断为少量用户。
- 模式：日常收件模式，直接写入。
- 轻反馈：`已收进 Bug池：待复现 / S1严重`，标题 `保存设置时报错 500 且多个账号失败`。补一句：`需尽快处理`。
- 原因：功能报错且描述了“以前可以现在不行”；虽然缺少环境、截图和完整复现步骤，但应先入池，后续集中处理时补证据。

## 示例 3：进入需求池，状态为待确认

输入：

```text
客户说如果系统能接入飞书审批，他们就更愿意推进采购。但目前不确定他们真实流程是什么，也不知道是不是硬性采购条件。
来源：销售反馈
```

处理：

- 拟写入池子：`需求池`
- 需求状态：`待确认`
- 优先级：`P1`
- 内部预处理字段：用户类型 `企业客户`，来源渠道 `销售`，影响范围 `核心客户`，业务价值 `高`。
- 模式：日常收件模式，直接写入。
- 轻反馈：`已收进需求池：待确认 / P1`，标题 `飞书审批集成可能影响采购推进`。补一句：`需尽快处理`。
- 原因：初步优先级为 `P1`，且采购条件和真实流程不清楚；但这类信息不足应通过状态 `待确认` 承接，而不是写入前打断。

## 示例 4：进入需求池，状态为待观察

输入：

```text
社群里有两个用户提到希望支持暗色模式，但没有展开原因。
来源：社群
```

处理：

- 拟写入池子：`需求池`
- 需求状态：`待观察`
- 优先级：`P3`
- 内部预处理字段：用户类型 `未知`，来源渠道 `社群`，影响范围 `少量用户`，业务价值 `低`。
- 模式：日常收件模式，直接写入。
- 轻反馈：`已收进需求池：待观察 / P3`，标题 `暗色模式弱信号`。
- 原因：反馈样本少，场景和业务影响不明确，暂不适合执行，但应继续记录。

## 示例 5：进入需求池，核心路径体验问题

输入：

```text
用户说首页信息太多，每次打开都不知道先看哪里，尤其是新建项目后找不到下一步该做什么。
```

处理：

- 拟写入池子：`需求池`
- 需求状态：`待执行`
- 优先级：`P2`
- 内部预处理字段：用户类型 `未知`，来源渠道 `其他`，影响范围 `广泛影响`，业务价值 `高`。
- 模式：日常收件模式，直接写入。
- 轻反馈：`已收进需求池：待执行 / P2`，标题 `首页信息过多导致新建项目后下一步不清晰`。
- 原因：新建项目后的下一步属于核心激活路径，问题和场景清楚；但当前只有一条反馈，暂缺量化影响和收入风险证据。

## 示例 6：集中处理收件箱

输入：

```text
今天收了哪些反馈？帮我处理一下待确认的需求和待复现 Bug。
```

处理：

- 模式：集中处理收件箱。
- 读取：`需求池` 和 `Bug池`。
- 排序：先 `P0/P1` 和 `S0/S1`，再待确认/待复现，最后待观察。
- 输出：按 `类型 / 标题 / 状态 / 优先级或严重程度 / 缺失信息 / 下一步` 给出处理队列。
