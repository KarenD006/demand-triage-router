# 需求分拣机

`demand-triage-router` 是一个面向产品经理日常工作的需求与 Bug 收件箱技能。它用于把聊天记录、截图、工单、表格、文档里的零碎反馈，自动分拣到飞书多维表格中的 `需求池` 和 `Bug池`，减少产品经理被每条反馈即时打断的成本。

当前版本：`0.3.3`

## 适用场景

- 初始化一个用于需求分拣的飞书多维表格。
- 接收用户、客户、销售、客服、运营等来源的零碎反馈。
- 自动判断反馈应进入 `需求池` 还是 `Bug池`。
- 为需求设置状态和初步优先级。
- 为 Bug 设置状态、严重程度，并记录原因反馈。
- 按状态集中查看待确认、待观察、待执行、执行中、开发中、已完成的需求。
- 按状态或严重程度集中查看 Bug。

不适用于直接替产品经理决定最终排期、完整 PRD 编写、项目计划管理或泛行业研究。

## 核心心智

这个技能把每条输入先当作“线索”，再判断它更像：

- `Bug池`：产品没有按预期工作，例如报错、不可用、数据丢失、以前能用现在不能用。
- `需求池`：产品诉求、体验问题、机会线索、弱信号或需要进一步确认的信息。

日常模式下，单条普通反馈默认自动写入飞书，不逐条要求用户确认。只有用户明确要求“先分析、先别写、等我确认”，或批量材料拆分不确定、写入可能覆盖重要字段时，才进入异常确认模式。

## 快速开始

在 Codex 中使用时，可以直接说：

```text
使用 demand-triage-router 初始化需求分拣机
初始化一下需求分拣skill
```

首次运行时，技能会：

1. 检查 `data/base-state.json` 是否已有可用飞书 Base 配置。
2. 如果没有配置或配置失效，创建一个新的飞书多维表格。
3. 在同一个 Base 中创建两张表：`需求池` 和 `Bug池`。
4. 补齐字段和常用视图。
5. 把 Base 链接、base token、表 ID 写入 `data/base-state.json`，供下次复用。

如果你想重新初始化，只需要删除 `data/base-state.json`。不要删除 `data/base-state.example.json`。

## 日常使用

直接把反馈发给 Codex，例如：

```text
帮我录个需求：
客户问能不能支持批量导出项目数据。他们每周都要整理项目进度给老板，现在需要一个个复制，很费时间。
```

技能会自动分析、分拣、写入飞书，然后轻量反馈：

```text
已收进需求池：待执行 / P2
标题：项目数据批量导出以支持周报汇报
```

Bug 示例：

```text
用户反馈上传附件时提示成功，但回到详情页看不到附件。换了 Chrome 和 Safari 都一样。
```

可能的反馈：

```text
已收进 Bug池：待复现 / S2一般
标题：附件上传成功后详情页不显示
```

## 更新处理进度

可以用自然语言更新已有记录：

```text
附件上传成功后详情页不显示，这个 BUG 已经解决了，标记已修复吧。问题是入库超长。
```

技能会把 Bug 状态更新为 `已修复`，并把 `入库超长` 写入 `原因反馈` 字段。`环境信息` 只用于设备、系统、浏览器、版本、账号、页面等复现环境，不用于记录根因或处理结论。

## 查询收件箱

需求查询示例：

```text
看一下待确认的需求
看一下待观察的需求
执行中的需求有哪些
今天都记录了哪些需求
```

Bug 查询示例：

```text
看一下待修复 Bug
严重 Bug 有哪些
还有哪些 BUG 没有反馈处理进度
```

集中处理时，技能会优先列出高优先级需求和严重 Bug，再列待确认、待复现、待执行、待观察等内容，并给出下一步建议。

## 需求池字段概览

`需求池` 用于承接非 Bug 的反馈。

| 字段 | 说明 |
|---|---|
| 需求标题 | 用一句话描述真实问题 |
| 用户原话 | 原始反馈或关键证据 |
| 真实问题 | 从反馈还原出的真实问题 |
| 使用场景 | 用户在什么任务或流程下遇到问题 |
| 用户类型 | 免费用户、付费用户、企业客户、内部用户、未知 |
| 来源渠道 | 客服、销售、社群、访谈、数据分析、应用商店、内部、其他 |
| 影响范围 | 单个用户、少量用户、多个客户、核心客户、广泛影响、未知 |
| 业务价值 | 高、中、低、未知 |
| 优先级 | P0、P1、P2、P3、未定 |
| 状态 | 待观察、待确认、待执行、执行中、开发中、已完成 |
| 缺失信息 | 需要补充的问题、场景、影响或约束 |
| 下一步动作 | PM 或团队接下来要做什么 |
| 负责人 | 可选负责人 |
| 来源附件 | 截图、文档、表格等原始材料 |
| 最近出现时间 | 最近一次出现该反馈的时间 |

## Bug池字段概览

`Bug池` 用于承接明确故障、异常、不可用、与预期不符、可复现或疑似可复现的问题。

| 字段 | 说明 |
|---|---|
| Bug标题 | 一句话描述异常 |
| 用户原话 | 原始反馈 |
| 复现描述 | 复现步骤；未知时写缺失项 |
| 期望结果 | 用户或产品预期 |
| 实际结果 | 实际发生了什么 |
| 严重程度 | S0阻塞、S1严重、S2一般、S3轻微、未知 |
| 环境信息 | 设备、系统、浏览器、版本、账号、页面 |
| 原因反馈 | 故障原因、根因、修复原因、处理结论；未知时留空 |
| 来源渠道 | 客服、销售、社群、访谈、监控、内部、其他 |
| 状态 | 待确认、待复现、待修复、修复中、待验证、已修复、无法复现、关闭 |
| 负责人 | 可选负责人 |
| 修复截止 | 需要时填写 |
| 来源附件 | 截图、录屏、日志、文档 |
| 最近出现时间 | 最近一次反馈时间 |

## 文件说明

- `SKILL.md`：技能入口和主工作流。
- `references/lark-base-schema.md`：飞书多维表格字段、视图和初始化规则。
- `references/triage-rules.md`：需求和 Bug 的分拣规则、状态判断、输出格式。
- `examples/sample-feedback-inputs.md`：典型输入和预期分拣结果。
- `data/base-state.example.json`：本地 Base 状态文件示例。
- `data/base-state.json`：运行后生成的真实配置文件，包含 Base 链接和表 ID；不要提交、分享或写入 README。

## 隐私和配置

- 不要把真实 `base-state.json` 提交到仓库或发给别人。
- 不要在文档中写入 app secret、access token、tenant access token、cookie 或其他凭证。
- 如果要重置技能状态，删除 `data/base-state.json` 即可。
- 示例文件中的 `base_token_here` 和 `https://example.feishu.cn/...` 是占位内容，不是真实配置。
