# 需求分拣规则

## 分拣心智模型

反馈不是需求。每条材料先被看作“线索”，再判断它更像：

- `Bug池`：产品没有按预期工作。
- `需求池`：产品诉求、体验问题、机会线索、弱信号和需要沟通确认的信息。

不要问 AI “这个需求该不该做”。日常场景先把反馈接住、分拣、入池，减少产品经理被打断；集中处理时再输出拟处理顺序、缺失信息和下一步建议。

## 提取字段

每条候选反馈先提取：

| 字段 | 提取方法 |
|---|---|
| 用户原话 | 保留原始表达；截图或文档中无法完整保留时写关键摘录 |
| 来源渠道 | 从上下文判断；不能判断写其他 |
| 用户类型 | 免费用户、付费用户、企业客户、内部用户、未知 |
| 使用场景 | 用户正在完成什么任务 |
| 可能真实问题 | 用户真正卡住的地方 |
| 影响范围 | 根据人数、客户数量、路径通用性和客户重要性判断 |
| 业务价值 | 根据采购、续费、转化、效率、激活、留存或体验价值判断 |
| 影响程度 | 是否阻塞、影响效率、影响收入、影响体验 |
| 原因反馈 | 仅 Bug 需要；记录用户、研发或排查结果明确给出的故障原因、根因、修复原因或处理结论 |
| 缺失信息 | 还需要什么才能判断或推进 |
| 拟入池 | 准备写入需求池或 Bug池 |
| 需求状态 | 仅需求池需要填写 |
| 优先级 | 需求池优先评定 P0/P1/P2/P3，只有无法判断时才用未定；Bug池用严重程度 |

## 内部预处理字段

日常收件模式下不展示完整分析，但内部必须先完成完整写入字段的预处理。写入时直接把这些预处理字段一起写入，不要到写入阶段统一填 `未知`、`其他` 或 `未定`。

兜底规则：

- 能从上下文合理推断时，就填写推断值。
- `未知`、`其他`、`未定` 不是默认值，只是缺少线索、信息冲突或字段不适配时的兜底。
- 如果字段是推断值，不需要在确认阶段额外展示；写入后也不需要再向用户解释不确定点。

### 用户类型

| 值 | 判定线索 |
|---|---|
| 企业客户 | 出现客户、采购、老板、管理员、组织、项目管理、审批、合同、续费等 B 端或组织场景 |
| 付费用户 | 明确提到已付费、订阅、会员、付费账号 |
| 免费用户 | 明确提到试用、免费版、未付费 |
| 内部用户 | 来源或主体是内部同事、销售、客服、运营、产品、研发 |
| 未知 | 没有任何身份、客户类型或使用主体线索 |

### 来源渠道

来源渠道记录“这条线索从哪里进入需求分拣机”，不是用户身份。

| 值 | 判定线索 |
|---|---|
| 客服 | 客服工单、客服转述、用户支持 |
| 销售 | 销售反馈、商机、采购推进、客户拜访 |
| 社群 | 用户群、微信群、飞书群、社区讨论 |
| 访谈 | 用户访谈、调研、回访 |
| 数据分析 | 埋点、漏斗、报表、监控数据 |
| 应用商店 | 应用商店评论、评分 |
| 内部 | 内部同事主动提出，不是转述外部用户 |
| 其他 | 只有“用户说/客户说”但没有渠道线索，或来源不属于以上类型 |

### 影响范围

| 值 | 判定线索 |
|---|---|
| 单个用户 | 只出现一个用户、一个账号、一次反馈，且不是通用核心路径 |
| 少量用户 | 两三个用户、几个账号、同一客户内多个成员 |
| 多个客户 | 多个客户、多家公司、多组织反馈 |
| 核心客户 | 大客户、关键客户、采购中客户、续费风险客户明确相关 |
| 广泛影响 | 首页、登录、注册、新建项目、保存、上传、导出、支付、权限等通用核心路径，即使当前只有一条反馈也可判定 |
| 未知 | 完全无法判断人数、客户范围或路径影响 |

### 业务价值

| 值 | 判定线索 |
|---|---|
| 高 | 直接影响采购、续费、付费转化、核心客户、关键流程完成、激活或明显效率收益 |
| 中 | 能改善常见流程效率、体验、留存或减少支持成本，但没有直接收入或核心客户证据 |
| 低 | 偏偏好、偏美观、影响范围窄，或只是低频便利性优化 |
| 未知 | 无法从反馈判断业务或用户价值 |

### 优先级

优先级是初步分拣建议，不是最终排期承诺。尽量评定，避免默认 `未定`。

| 优先级 | 判定线索 |
|---|---|
| P0 | 核心功能不可用、严重阻塞业务、数据丢失、高风险线上事故 |
| P1 | 影响采购、续费、付费转化、核心客户、关键业务流程，或多个客户反复反馈 |
| P2 | 场景清楚、问题明确，能改善效率、体验、激活或留存，但暂缺强收入或大范围证据 |
| P3 | 弱信号、偏体验、个体偏好、影响较小，适合观察或低成本优化 |
| 未定 | 信息互相矛盾、完全无法判断，或用户明确要求暂不评定 |

## 收件模式

接受单条普通反馈后，默认使用 `日常收件模式`：自动分析、自动分拣、自动写入飞书，然后用一句话轻反馈。不要让产品经理为每条碎片需求做确认。

轻反馈格式：

```text
已收进需求池：待执行 / P2
标题：首页信息过多导致新建项目后下一步不清晰
```

或：

```text
已收进 Bug池：待复现 / S2一般
标题：上传附件成功后详情页不显示
```

## 异常确认

只有命中异常确认条件时，才先轻量确认。高优先级需求或严重 Bug 不是确认条件，应先入池，再在轻反馈里提醒尽快处理。

异常确认条件：

- 用户明确说“先别写入”“先分析一下”“等我确认”“不要自动入池”。
- 批量材料拆成多条候选项，拆分边界、归类或优先级不确定。
- 写入会删除记录、覆盖重要字段、降低优先级或严重程度、改变已有记录池子，且无法通过新增记录或追加证据安全处理。
- 信息不足但必须二选一时，优先选择更保守的可追踪写法，不要为了确认而打断：疑似 Bug 进 `Bug池/待确认` 或 `待复现`；疑似需求进 `需求池/待确认`。
- `P0/P1` 需求或 `S0/S1` Bug 默认直接入池，并在轻反馈里提示“需尽快处理”。

确认不要使用固定开头，确认内容保持轻量。

需求池确认只输出：

| 字段 | 说明 |
|---|---|
| 用户原话 | 两行以内摘要；过长时用 `...` 省略 |
| 拟入池 | 需求池 |
| 需求状态 | 待观察、待确认、待执行、执行中、开发中、已完成 |
| 优先级 | P0、P1、P2、P3、未定 |

Bug池确认只输出：

| 字段 | 说明 |
|---|---|
| 用户原话 | 两行以内摘要；过长时用 `...` 省略 |
| 拟入池 | Bug池 |
| Bug状态 | 待确认、待复现、待修复、修复中、待验证、已修复、无法复现、关闭 |
| 严重程度 | S0阻塞、S1严重、S2一般、S3轻微、未知 |

异常确认语自然即可，例如：

```text
我准备这样记录：

| 用户原话 | 拟入池 | 需求状态 | 优先级 |
|---|---|---|---|
| 客户希望批量导出项目数据，每周整理项目进度给老板... | 需求池 | 待执行 | P2 |

这样写可以吗？你也可以直接改状态或优先级。
```

异常确认模式下，只有用户明确确认后，才执行飞书写入。用户要求修改时，先修正拟入池、状态或优先级，再重新等待确认。

## 拟写入池子判断顺序

### 1. 先判 Bug

符合任一条件，优先进入 `Bug池`：

- 功能报错、无法打开、无法保存、无法登录、数据丢失。
- 用户描述“以前可以，现在不行”。
- 实际结果与已知产品规则、文档、预期不一致。
- 需要工程排查、复现、修复。

如果复现信息不足，仍可进 `Bug池`，状态设为 `待复现` 或 `待确认`。

### 1.1 Bug 原因反馈

- 新增 Bug 时，只有材料里已经明确出现原因、根因、处理结论时才写 `原因反馈`；不知道原因时留空。
- 更新 Bug 处理进度、标记 `已修复`、`无法复现`、`关闭` 时，如果用户提供“问题是...”“原因是...”“根因...”“处理备注...”等信息，必须写入 `原因反馈`。
- `环境信息` 只放设备、系统、浏览器、版本、账号、页面、日志入口等复现环境，不承载原因或处理结论。

### 2. 其余进入需求池

非 Bug 的反馈都进入 `需求池`，再用 `状态` 区分后续处理：

| 状态 | 使用条件 |
|---|---|
| 待观察 | 信号还弱、证据不足、短期不适合动作但不应丢弃 |
| 待确认 | 需要进一步和需求方沟通，补充场景、真实问题、影响范围、约束或验收口径 |
| 待执行 | 需求已经清楚，具备产品经理开始处理的条件 |
| 执行中 | 产品经理正在处理，处于原型、方案、文档或评审阶段 |
| 开发中 | 已经移交开发，正在研发处理中 |
| 已完成 | 已上线、已修复、已交付或用户明确说完成 |

一句话反馈不天然进入 `待确认`。如果它已经包含场景、痛点和影响，可以进入 `待执行`；如果只是弱信号，进入 `待观察`；如果缺少关键场景或真实问题，才进入 `待确认`。

## 去重和聚类

写入前先检查是否存在同类问题。日常收件模式允许自动更新同类记录；如果合并边界不清楚，优先新增一条并在 `下一步动作` 标注“需与疑似同类记录合并判断”。只有会覆盖关键状态、降低优先级或改变池子且无法安全自动处理时，才进入异常确认。

- 相同真实问题、相同场景、相同用户类型，优先更新已有记录。
- 用户表达不同但真实问题相同，可以更新到同一条记录。
- 用户表达相似但真实问题不同，不要合并。

更新已有需求记录时，至少更新：

- `用户原话` 增加新证据摘要。
- `来源渠道`。
- `最近出现时间`。
- 必要时更新 `状态`、`优先级` 和 `下一步动作`。

## 查询需求状态

用户说“看一下待确认的需求”“待观察需求有哪些”“执行中的需求”“开发中的需求”“已完成需求汇总”等时：

1. 读取 `需求池` 字段结构。
2. 按 `状态` 精确筛选。
3. 输出需求明细。

输出格式：

| 需求标题 | 用户原话摘要 | 使用场景 | 缺失信息 | 下一步动作 | 负责人 | 最近出现时间 |
|---|---|---|---|---|---|---|

## 集中处理收件箱

用户说“今天收了哪些”“最近收了哪些反馈”“处理一下待确认需求”“帮我整理 P1/P2”“看一下待复现 Bug”等时，进入集中处理流程。

处理顺序：

1. 先列 `P0/P1` 需求和 `S0/S1` Bug。
2. 再列 `待确认` 需求和 `待复现 / 待确认` Bug。
3. 然后列 `待执行` 需求和 `待修复` Bug。
4. 最后列 `待观察` 需求。

输出格式：

| 类型 | 标题 | 状态 | 优先级/严重程度 | 缺失信息 | 下一步 |
|---|---|---|---|---|---|
| 需求 | 首页信息过多导致新建项目后下一步不清晰 | 待执行 | P2 | 需确认新建项目后的关键路径 | 梳理首页层级和新建项目引导 |

Bug 明细中如存在 `原因反馈`，优先展示在缺失信息或下一步前，便于产品经理快速判断处理进度。

## 用户反馈格式

日常收件模式，写入后轻反馈，不要输出长分析表：

```text
已收进需求池：待执行 / P2
标题：项目数据批量导出以支持周报汇报
```

异常确认模式，确认前轻量反馈，并明确准备写入哪个池子、状态和优先级：

| 用户原话 | 拟入池 | 需求状态 | 优先级 |
|---|---|---|---|
| 用户说每周整理项目进度给老板，只能逐个复制... | 需求池 | 待执行 | P2 |

批量写入或异常确认后，用写入结果表反馈：

| 用户原话 | 写入池子 | 状态 | 优先级 | 写入方式 | 下一步 |
|---|---|---|---|---|---|
| 用户说每周整理项目进度给老板，只能逐个复制... | 需求池 | 待执行 | P2 | 新增或更新同类需求 | 补充导出字段、汇报格式和影响范围 |

如果没有写入飞书，额外说明原因：

- 缺少 Base token 或链接。
- 缺少权限。
- 字段结构不匹配。
- 命中异常确认条件，用户尚未确认反馈分析。
- 用户只要求先分析，不要求写入。
